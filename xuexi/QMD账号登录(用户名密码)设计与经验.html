QMD 用户名密码登录 · 设计与经验沉淀

自建账号 + 可替换凭证校验 · 2026-09-15 · 基于 MinerU-Document-Explorer 现网实现

一、背景与结论

原 QMD 的 API 鉴权只有一种方式：CLI/管理员用 qmd user add 生成的 Bearer token（写入 tokens.json）。 这对“人”使用不够友好——要手动复制粘贴一长串 token。本次新增用户名 + 密码登录能力，并保留原有 token 体系兼容。

产品结论（与需求方确认）：
  • 账号先由 QMD 自建，但把“凭证校验”抽象成可替换函数，预留对接你方已有身份库。
  • 密码存在现有文件用户库（~/.config/qmd/users/<id>.json 增加字段），零新增依赖。
  • 登录签发的 token 不过期，与现有 CLI token 一致（内网/可信环境足够简单）。
  • 安全做到加强版：scrypt 哈希 + 统一 401 + 登录限流 + 退出登录 + 失败日志。

二、数据模型

用户文件 ~/.config/qmd/users/<userId>.json 新增两个字段，其余结构不变：

{
  "name": "Alice",
  "username": "alice",              // 新增，唯一（用户名登录用）
  "passwordHash": "scrypt$<saltHex>$<hashHex>", // 新增，scrypt 哈希
  "createdAt": 1730000000000,
  "settings": {}
}

字段写入位置：src/settings.ts 中 createUser 与 setUserPassword（见第四节行号）。

tokens.json 结构完全不变：{ "<token>": "<userId>" }。登录成功后把新 token 写进它，复用现有 resolveUser 解析链路，无需改动 token 解析逻辑。

兼容性：只有 name、没有 password 的“老用户”（纯 token 用户）依旧只能用手动粘贴 token 的方式使用； 只有设了 username + password 的账号才支持用户名登录。两种方式并存，互不干扰。

三、架构：可替换的凭证校验

登录端点不直接读文件，而是调用一个抽象的 CredentialVerifier。默认实现是文件式，未来接 LDAP / 既有用户库 / OIDC 时，只需实现同一接口并 setCredentialVerifier(...)，登录端点零改动。

// src/auth.ts
export interface CredentialVerifier {
  verify(username: string, password: string): Promise<string | null>; // 返回 userId 或 null
}
export const fileBasedVerifier: CredentialVerifier = {
  verify: (u, p) => Promise.resolve(fileVerifyCredentials(u, p)),
};
let active = fileBasedVerifier;
export const setCredentialVerifier = (v) => { active = v; };
export const getCredentialVerifier = () => active;

接口定义：src/auth.ts:13。登录端点使用：src/api/server.ts 中 getCredentialVerifier().verify(...)。

六、使用方式

1) CLI 创建可登录账号

# 交互式输入密码（推荐，密码不进 shell 历史）
qmd user add "Alice" --username alice

# 一条命令带密码（会进进程参数/历史，生产慎用）
qmd user add "Alice" --username alice --password 'S3cret!'

# 给已有（无密码）用户补设密码
qmd user set-password alice
qmd user set-password alice --password 'NewPass1'

# 列出 / 吊销（token 体系，原有能力）
qmd user list
qmd user revoke <token>

密码留空时走交互式 readline 输入到 stderr；createUser 会校验用户名唯一性，重复会抛 用户名已存在。

2) API 直接调用

# 登录
curl -s -X POST http://localhost:8787/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"S3cret!"}'
# => {"token":"","userId":"...","name":"Alice","username":"alice"}

# 用返回的 token 访问受保护接口
curl -s http://localhost:8787/api/config -H "Authorization: Bearer "

# 退出登录（吊销当前 token）
curl -s -X POST http://localhost:8787/api/auth/logout \
  -H "Authorization: Bearer "
# => {"ok":true}

3) 前端

  • 无 localStorage.qmd_token 时自动弹出登录卡片；登录成功后存 token 并进入主界面。
  • 顶栏新增「退出登录」按钮：调 /api/auth/logout 并清 localStorage。
  • 「配置」面板保留手动粘贴 token 入口，兼容 CLI/管理员 token。
  • 若请求返回 401（token 失效/无权限），前端自动回到登录态。

七、安全要点

  • 密码哈希：scrypt + 每账号随机 16 字节 salt，存储 scrypt$salt$hash；校验用 crypto.timingSafeEqual 防时序侧信道。
  • 防爆破：登录接口 per-IP 滑动窗口限流（默认 5 次/分钟，超过返回 429）。
  • 防用户枚举：用户名不存在 / 密码错误统一返回 401 {"error":"用户名或密码错误"}，不暴露差异。
  • 失败日志：每次失败在 stderr 打印 [auth] login failed ip=... user=... 时间，便于后续接告警。
  • 退出登录：服务端吊销 token（从 tokens.json 删除），前端清 localStorage。
  • 匿名访问开关：默认要求鉴权；仅 QMD_ALLOW_ANONYMOUS=true 才放行无 token 访问（src/api/server.ts:114），用于本地开发。

八、踩坑与经验（实现记录）

1. noUncheckedIndexedAccess 下 split 结果索引为 string | undefined

storedHash.split("$")[1] 在严格索引检查下是 string | undefined，直接 Buffer.from(parts[1], "hex") 会报类型错。 修正：先解构到具名变量并做空值判断 if (!saltHex || !expectedHex) return false; 再 Buffer.from。 （src/settings.ts:231 的 verifyPassword）

2. readline/promises 的 question 返回 Promise，不能用回调

Node 的 readline/promises 里 rl.question(q) 直接返回 Promise<string>，没有回调形态。 最初写成 rl.question("", (ans)=>resolve(ans)) 被 TS 报错（类型不匹配 Abortable）。 修正：封装 promptPassword() 用 await rl.question(prompt)，并在 finally 中 rl.close()。 （src/cli/qmd.ts）

3. createUser 用户名唯一性在写文件前校验

findUserByUsername 遍历 users/ 目录。由于新建用户的文件在唯一性检查之后才写入，不会误判自己； 但重复用户名会抛 用户名已存在，CLI 需 try/catch 友好提示（已处理）。

4. 自测要清理测试数据

测试在真实 ~/.config/qmd 下创建用户/ token。初版因脚本断言失败在 cleanup 前中断， 遗留了一个 "alice" 测试账号，导致重跑时 createUser 触发“用户名已存在”而误以为逻辑出错。 经验：清理逻辑放进 finally，并用随机化用户名（authtest_xxxx）避免碰撞。

5. 端到端测试需显式 dbPath

startApiServer 不允许隐式落到全局索引库（会抛 Database path not set）。 测试时给一个 os.tmpdir() 下的临时 sqlite 路径即可。

九、预留：对接你方已有身份库

只需新建一个实现了 CredentialVerifier 的对象，再在启动 API 前调用 setCredentialVerifier(...)， 或后续按环境变量切换默认实现。登录端点、限流、失败日志、issueToken 这套流程全部复用，无需改 server 代码。

import { setCredentialVerifier } from "./auth.js";
setCredentialVerifier({
  verify: async (username, password) => {
    // 调用你们既有用户库 / LDAP / OIDC ...
    return externalUserIdOrNull;
  },
});

注意：对接外部库时，登录成功后的 userId 应映射到 QMD 侧的 users/<id>.json（用于 settings 隔离）， 可为外部用户预建/绑定一个 QMD userId。
