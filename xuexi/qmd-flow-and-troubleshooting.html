一、项目主流程：QMD 混合检索一次 query 在内部发生了什么

这是项目本身的核心链路。用户的一次查询会经过「多路召回 → 融合去重 → 精排」三个阶段，其中每个阶段依赖不同的本地模型。

    DB-->>SS: 语义候选集
    SS->>SS: RRF 加权融合并去重

    LLM->>RR: 拼接查询与文本块做完整前向
    RR-->>LLM: 返回该对相关性分数
    LLM-->>SS: 重排后的候选列表

    SS->>SS: 融合位置分与重排分得到最终得分
    SS-->>CLI: Top K 结果含 docid 分数片段
    CLI-->>U: 输出命中文件与内容摘要

注意图中「请求对候选块重排」这一步：重排模型是 cross-encoder，每个候选都必须和查询拼起来独立跑一次完整前向，无法像嵌入那样批量复用——这是整条链路在 CPU 上最昂贵的地方。

三、优化后的调用时序常驻服务带来的差异

改动生效后，模型只在首次调用时加载一次，之后所有请求直接复用内存中的模型。

    participant MEM as 常驻模型

    Note over CB,MEM: 首次调用 需要把模型读进内存
    CB->>SVC: 握手并列举可用工具

这也解释了实测中出现的 8.3 秒：两次请求间隔超过空闲阈值，上下文被回收后重建所致。它依然远好于从磁盘重新加载模型的 205 秒——因为权重仍在内存中。

四、原理解析：CPU 推理为什么慢为什么偏偏卡在重排

同一台机器上，嵌入只要十几秒，重排却要十分钟以上。差别不在模型的绝对大小，而在架构范式与访存模式这两件事。

把上面那条链路换成算式，实测数字就能对上了：

  • 第一步 · 单 token 成本：15 GB/s ÷ 0.64 GB ≈ 23 token/秒。batch=1 时算力大量闲置，瓶颈纯粹是「搬数据」而不是「算」。
  • 第二步 · 单个 pair：约 1200 token ÷ 23 ≈ 52 秒。
  • 第三步 · 整批：52 秒 × 7 ≈ 6 分钟，再叠加加载模型与创建上下文的固定开销 → 与实测十分钟以上吻合。
  • 对照 · 嵌入为什么快：模型约 0.32 GB → 约 47 token/秒；但真正的关键是文档向量早已离线算好存进 SQLite，在线只需为查询本身算一次，而查询只有几十个 token。
一个容易踩的坑：「开 GPU 」并不总是更快。独立显卡的显存带宽比内存高一到两个数量级，确实会快；但集成显卡是共享系统内存的，带宽没有提升，反而多了数据搬运与调度开销——源码 llm.ts 的注释里就明确记录了这个案例：同一批重排任务，走集显卸载是 261 秒，走多线程 CPU 反而是个位数秒。所以当前默认走 CPU 是有依据的。

六、遗留事项与运维要点

  • 常驻服务成为前置依赖：原来的进程方式会随用随起，现在必须先有常驻服务。重启电脑或进程被杀后需要用 qmd mcp --http --daemon 恢复，可用 qmd status 查看、qmd mcp stop 停止。
  • 仅监听 IPv6：本地端口不看 IPv4，127.0.0.1 连不上，localhost 与 [::1] 可以。日后若用非 Node 客户端调用其 REST 接口，请显式使用 IPv6 形式。
  • 空闲回收机制：超过五分钟无请求会释放上下文，下次请求透明重建（数秒）。模型权重不清空，所以仍远快于冷启动。
  • 重排已默认关闭：命令行与 MCP 工具的完整检索现在默认跳过重排，耗时从 270 秒以上降到约 9 秒；需要最高精度时用 --rerank 或参数 skipRerank: false 手动开启。精排本身的性能优化（换更低量化、收窄上下文）只在开启它时才有意义，暂未处理。
  • 全文检索对中文无效：纯关键词检索对中文分词失效导致零结果，中文场景请使用向量检索或混合检索路径。
  • 配置回滚：原配置已备份为 C:/Users/wuzhu/.codebuddy/mcp.json.bak-20260907-182828。
  • 命令行其实是两份，改完源码要同步：直接敲 qmd 用的是全局安装的包（位于 node 安装目录下的 node_modules/mineru-document-explorer，它执行自己的 dist/ 编译产物），与项目源码是两份不同代码。修改源码后必须重新构建并把 dist 覆盖过去才会生效；嫌麻烦就直接用 npm run qmd，它走源码，永远是最新。判断是否同步的办法：where qmd 看它是否指向项目目录。
