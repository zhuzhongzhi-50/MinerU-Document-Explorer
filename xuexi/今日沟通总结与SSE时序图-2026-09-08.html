MinerU Document Explorer（QMD）— 今日沟通总结与 SSE 时序图

日期：2026-09-08 ｜ 主题：RAG 检索架构答疑 + 查询四阶段「每步真实输出」流式改造 ｜ 文档性质：可 A4 打印

一、今日沟通主线

你今天沿「配置参数抽象 → 加 HTTP API 层 + 接问答 API → 前端页面」一路把 QMD 做完了，核心疑问有两条，最后落地为一次具体的代码改造：

  1. 架构疑问：为什么接了「问答 API」之后，打开 html 仍然「要嵌入模型」？是不是重复/多余？
  2. 体验需求：前端 loading 那四个阶段（嵌入模型 / 扩展模型 / 重排 / 生成答案）只是「假进度条」，要求把每一步的真实中间产出也显示出来。

最终我们把 POST /api/query 从「一次性返回 JSON」改成了 SSE 流式，把检索各阶段（扩展 / 嵌入 / 重排）的真实数据与答案 token 实时推送到前端，并实测验证通过。

二、遇到的问题与解决

问题 1 架构误解 — 为什么还要本地嵌入模型？

现象：你接了「问答 API」（生成层），打开 HTML 提问却仍提示要加载「嵌入模型」，以为重复劳动。

根因：混淆了 RAG 的两个独立环节。问答 API 只负责「根据资料写答案」（Generation），而「从你的文档库里找出最相关片段」这一检索步（Retrieval）本身就依赖嵌入模型把文档切块成向量、并把问题也向量化去做语义匹配。没有检索，LLM 只能凭空编（幻觉）。所以问答 API 替代不了 embedding。

澄清点：

  • 嵌入模型有两个用途：①建库时嵌入文档（按集合一次性）；②每次查询时嵌入「问题」去向量库匹配。后者无法省。
  • 文档 embedding 是按集合一次性写入的（store.ts 只挑缺失的块），已 embed 的集合查询是秒回的。
  • UI 上的「嵌入模型」字样有一半是错觉：它是前端硬编码的第一阶段，即使后端实际跳过了嵌入，UI 也会先亮它——属于「假进度」。

结论：嵌入模型不能省；你感知到的「要嵌入」多半是换了一个还没建向量的集合，或纯前端假进度。

问题 2 功能实现 — 让四阶段每步真实输出可见

现象：前端四阶段是纯前端推测进度（app.js 注释自述「非后端真实进度」），真实阶段信息（扩展了哪些词、嵌入耗时、重排候选数、答案逐字）全部被丢弃。

根因：/api/query 一次性返回最终结果，调用 store.search() 时没有透传 SearchHooks——而 hybridQuery 其实已内置了 onExpand / onEmbedStart / onEmbedDone / onRerankStart / onRerankDone 五个回调，数据本就存在，只是没接出来。

解决：把 /api/query 改成 SSE 流式，把 hooks 真实数据逐一 send(event, data) 给前端；答案在 rag.ts 改为逐 token 流式；前端读流并按事件渲染。改动清单见第三节。

问题 3 验证排查 — curl 一直返回 "Invalid JSON body"

现象：用 curl -d "{\"query\":\"...\"}" 测 SSE，后端始终回 {"error":"Invalid JSON body"}，一度怀疑是代码没生效。

根因：PowerShell 引号转义把 -d 的内容传坏，服务端 safeParse 收到的不是合法 JSON。与代码无关（旧接口同样返回该错）。

解决：改用临时 JSON 文件 + curl --data-binary @file，绕开 shell 引号。随后 SSE 正常返回，证明确实是新代码在跑。

问题 4 性能 — 首次查询等了 10 分钟

现象：第一次提问迟迟不出结果。

根因：首次要加载嵌入模型 + 扩展模型（本地 llama.cpp）。实测本次扩展模型首次加载耗时 ~116 秒；模型默认有闲置回收，反复冷启动就会很慢。

解决：此前已将模型设为常驻（inactivityTimeoutMs = 0）。首次预热后后续查询秒回。重启服务后第一次仍慢（加载模型），属正常。

问题 5 运行/运维 — 浏览器「127.0.0.1 拒绝了我们的连接请求」

现象：浏览器访问 127.0.0.1:8787 提示「拒绝了我们的连接请求」。诊断发现 8787 端口无任何进程监听，此前用后台方式拉起的新进程（PID 13412）已退出。

根因：用命令行工具以「后台方式」（如 PowerShell Start-Process）拉起的服务进程，归属工具临时 shell 的会话/作业（job）。命令执行完、shell 一退出，整棵进程树被一起回收——所以进程只活了几秒（够响应一两次健康检查），随后即死、端口空出。这也解释了为何 serve.out.log 里能看到 "running" 却连不上。

对照：你原先在终端手动 npm run qmd -- serve 启动的 18052 进程是稳定的——因为它在你自己一直开着的终端会话里常驻，不受工具 shell 影响。

解决：改用 WMI 独立会话拉起——通过 Win32_Process.Create 在系统会话创建进程，脱离工具 shell 的 job，不再被回收。验证 PID 1176 持续监听 8787，间隔多次查询均存活。临时启动脚本（serve_run.bat / start_serve.ps1）在确认常驻后已删除。

注意：

  • 用命令行工具「后台启动」本项目服务不可靠（会被回收）；需常驻时请在自己一直开着的终端里 npm run qmd -- serve，或采用 WMI / 计划任务等独立会话方式。
  • 当 8787 端口空闲（旧进程已死）时直接启动即可一次绑定成功；若旧进程未死会报端口冲突——此时先结束占用进程再启动。

以下问题 6–13 来自 2026-09-07 的排障会话（今天 SSE 流式改造的前置积累），一并归档于此，方便整体回顾。

问题 6 挂死 — qmd query 卡在 Expanding query 无输出

现象：命令行 qmd query 一直停在扩展阶段，没有任何返回。

根因：底层 evaluate 正常 → 卡点在会话封装层；模型已缓存，排除首次下载。最终定位为推理依赖（node-llama-cpp）的会话接口缺陷。

解决：升级 node-llama-cpp 3.17.1 → 3.20.0（安装时遇「安全删除保护转交回收站超时」，关闭该保护后重装成功）；类型检查零改动通过。

问题 7 挂死 — 升级后查询扩展仍卡死（grammar 死循环）

现象：升级依赖后，带语法约束（grammar）的查询扩展依旧永久卡住。

根因：隔离对照——纯 prompt 自由生成 41s 正常，带 grammar 的 180s 超时；报错指向结束符 token 类型异常。主责在上游采样器、诱因是分词器，qmd 无责，且该缺陷旧版也存在。

解决：查询扩展弃用 grammar 约束，改为自由生成 + 容错行解析。可稳定产出 lex / vec / hyde 三类查询变体。

问题 8 性能 — 杀软实时扫描 ~2GB 模型文件拖慢加载

现象：首次冷查询 141s，第二次仅 11s，冷热差异巨大。

根因：第三方安全软件对 GGUF 大文件实时扫描（本次复测时段系统自带防护已停用，实际扫描者是第三方杀软，且无命令行排除接口）。

解决：在其界面把模型目录（models/）单独加入信任区——不要扩大到整个缓存目录（索引库和日志很小，排除它们只会不必要地扩大安全口子）。冷查询降到秒级。

问题 9 性能 — 重排（cross-encoder）环节异常缓慢

现象：完整检索超过 4 分钟，客户端直接超时。

根因：重排是 cross-encoder，查询须与每个候选块逐对拼接、各自跑一次完整前向，无法批量复用；低压 CPU 内存带宽受限（~15GB/s），每 token 要把整套 640MB 权重读一遍（单 pair 40–70s × 候选数 + 固定开销 → 10min+）。候选降到 3 个仍超 10min，固定开销才是大头。

解决：① 先用纯向量检索绕开精排跑通链路；② 把自带的「跳过重排」开关接到命令行与工具层并默认关闭（需最高精度时 --rerank 或 skipRerank:false 手动开）。完整检索从 270s+ 降到 ~8.9s。

问题 10 加速 — 每次调用都重复加载模型（常驻服务）

现象：即便绕开精排，每次调用仍花 ~205s 重新加载模型。

根因：重复加载模型是每次调用的固定成本。

解决：启动常驻服务让模型只加载一次、常驻内存；并清理无用死代码（如已不用的 createGrammar）。连续两次调用：首次 205.4s → 第二次 1.2s，提速 164×。

问题 11 连接 — 客户端接常驻服务：127.0.0.1 连不上，localhost 可

现象：改为连接常驻服务后，127.0.0.1 拒绝连接，localhost / [::1] 正常。

根因：常驻服务仅监听 IPv6（127.0.0.1 是 IPv4）。Node 解析 localhost 可用，非 Node 客户端需显式用 IPv6 形式。

解决：用户级配置由「进程方式」改为「直连本地端口」。验证 status 4ms、检索 8.3s（间隔超空闲阈值上下文回收重建，仍远快于冷启动）。

问题 12 配置坑 — 敲 qmd 走全局包，改源码不生效

现象：改了项目源码，运行 qmd 却看不到效果。

根因：命令行有两份——直接敲 qmd 走全局安装包（执行自己的 dist/ 编译产物），与项目源码是两套不同代码。改源码须重新构建并覆盖 dist 才生效。

解决：开发期直接用 npm run qmd（走源码，永远最新）。判断依据：where qmd 看是否指向项目目录。

问题 13 检索 — 中文关键词（BM25）检索零结果

现象：用中文关键词做纯全文检索返回空。

根因：SQLite FTS5 对中文分词失效。

解决：中文场景请使用向量检索或混合检索路径，不要依赖纯 BM25。

以下问题 14–17 为 2026-09-08 当天主线实现工作（配置参数抽象 → 加 HTTP API 层 + 接问答 API → 前端页面），以「目标 / 解决」形式与前述故障类问题并列归档。

问题 14 配置 — 把散落的配置参数抽象成统一配置层

目标：原先运行参数分散在 CLI、llm、store 多处硬编码，改一项要翻几个文件，也无法经网页动态调整。

解决：新增 src/settings.ts 集中定义配置结构；src/api/server.ts 暴露 GET/PUT /api/config（merge + 持久化）与 POST /api/config/reset，配置可经 HTTP 动态读写并落盘（第六章验证日志中可见 /api/config 的调用）。

问题 15 API 层 — 新增 HTTP API 层并支持 SSE 流式推送

目标：要接网页前端就需要 HTTP 接口；且要把检索各阶段实时推到前端（见问题 2）。

解决：新增 src/api/，/api/query 改为 SSE（text/event-stream），构造 SearchHooks 把 expand/embed/rerank 事件 send 给前端，答案 token 经 onToken 推 token 事件，结束 send("done")；并加客户端断开兜底（req.on("close")），避免前端关页面后服务端空跑。

问题 16 问答 API — 接入问答 API 并改逐 token 流式

目标：答案要由你接的「问答 API」生成，且需与 SSE 阶段流同步、逐字蹦出。

解决：src/rag.ts 的 GenerateAnswerOptions 新增 onToken?；generateAnswer 改用 stream:true 解析 SSE delta 逐 token 回调；当问答 API 不返回 token 时降级为非流式请求，保证兼容。

问题 17 前端 — 前端读取 SSE 流并实时渲染每步产出

目标：HTML 要展示四阶段真实输出 + 流式答案，且阶段顺序要与后端真实一致。

解决：src/web/index.html 新增 #stageOutput / #liveAnswer 容器；src/web/app.js 读 response.body SSE 流，按 expand/embed/rerank/generate/token/done/error 事件实时渲染；阶段标记由后端事件驱动（不再前端瞎猜）；并修正阶段顺序为真实的 扩展模型 → 嵌入模型 → 重排 → 生成答案。

四、系统架构（RAG 两阶段）

检索层（Retrieval，依赖嵌入模型）：问题 → 查询扩展（lex/vec/hyde）→ 向量化问题 → 向量库 + BM25 混合召回 → 重排 → 返回最相关片段。

生成层（Generation，即你接的「问答 API」）：片段 + 问题 → LLM → 带引用标记的答案。

两层独立：嵌入模型属于检索层，问答 API 属于生成层，二者不能互相替代。
