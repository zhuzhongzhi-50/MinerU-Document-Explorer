2.1 模块划分与调用 / 数据流

定义："模块划分"指系统被拆成哪些职责单一的单元；"调用 / 数据流"指一次请求从入口到落库再回显，经过了哪些单元、传递了什么数据。二者共同构成系统的静态结构与动态行为两层视图。

目的：① 定位问题——报错时能快速判断是哪一层；② 评估改动影响——新增功能应落在哪一层、会不会波及既有模块；③ 复用能力——明确哪些是可复用资产（检索、LLM 出口），避免重复造轮子。

2.1.1 分层模型：先建立骨架

理解本系统最有效的方式是把它看成五层。分层的目的不是炫技，而是隔离变化——某一层的实现被替换时，其他层不受影响。这正是第三部分"兼容性改动"能够成立的根本原因：新增能力只落在业务层与存储层的增量部分，接入层与应用层几乎不动。

层级包含模块职责类比
接入层src/web/、scripts/接收人（浏览器）或机器（脚本）的指令，并展示结果餐厅前台与菜单
应用层src/api/server.ts、qmd CLI路由分发、参数校验、鉴权、错误兜底；本身不含业务逻辑传菜员，只负责送单
业务层src/intake.ts、src/contract-review/真正的领域逻辑：信息收集、合同审查厨师，按菜谱做菜
能力层hybridQuery、LLM 出口（settings）可复用的通用能力：混合检索、模型调用灶台与食材，谁都能用
存储层src/db.ts、src/db-schema.ts、src/store.tsSQLite 持久化、文档读写、索引维护仓库与冷库

关键约束（务必记住）：依赖方向严格自上而下——接入层可调用应用层，应用层调用业务层，业务层调用能力层与存储层；反向调用不存在（例如 db.ts 绝不会反过来调用 contract-review/）。这条单向依赖保证了模块可独立测试、独立替换，也是判断"改动是否安全"的第一准则。

2.1.3 数据流逐步解读（归纳为三条主链路）

图中连线较多，实际可归纳为三条主链路。理解这三条，就理解了整个系统的动态行为。

链路一 · 信息收集链路（人机协作采集）

  1. 发起：用户在浏览器操作，前端经 HTTP 调用 /api/intake/*。
  2. 分发：API 层 做参数校验后，把请求转给 src/intake.ts。
  3. 生成问题：intake.ts 把完整对话历史交给 LLM，让它"一次只问一题"——刻意避免一次抛出十个问题让用户无从下手。
  4. 降级：若 LLM 不可用（超时 / 未配置），intake.ts 切换为确定性兜底问题（内置题库），保证流程不中断。
  5. 沉淀：采集完成的摘要经 /api/wiki/save → store.writeDocument 写入 wiki。

适用场景：需求方自己也说不清要什么，需要通过多轮追问逐步澄清的场景。注意事项："一次只问一题"是刻意设计，若改成批量提问，用户回答质量会显著下降。

链路二 · 合同审查链路（本次新增，反向视角）

  1. 触发：scripts/ 直接调用 contractDrivenReview()——绕过 HTTP，因为耗时长，挂在 HTTP 上极易超时。
  2. 分句：splitClauses() 按"第 X 条 / 段落"把合同切成片段，并过滤短于 24 字的无意义段。
  3. 反查：每个片段调用 hybridQuery 在 wiki 域检索背景材料（限域检索，避免与合同原文混排）。
  4. 判定：把"片段原文 + 检索到的 wiki 依据"一起交给 LLM，让它标记 expected（标准清单已覆盖）/ unexpected（清单没写但确有风险）。
  5. 增量落盘：每处理完一个片段就写一次 -partial.md，长任务被中断也不丢失已审结果。

适用场景：手握一份合同、怀疑"标准清单之外还有坑"的场景。注意事项：耗时与片段数成正比，必须用 MAX_FRAGMENTS 控规模（调试建议先设 5）。

链路三 · 知识回流闭环（越用越聪明的关键）

  1. 采集或审查产出的内容写入 wiki 集合。
  2. store.writeDocument 因 autoEmbedOnWrite 开启，写完立刻建索引（无需额外的重建索引步骤）。
  3. 下一次检索（无论问答还是审查）即可命中这批新内容。
  4. 新内容又作为"知识库依据（wiki）"出现在新报告里，形成正循环。

为什么重要：没有这条闭环，知识库只进不出、逐渐陈旧；有了它，系统每次使用都在为下一次积累语料。本次报告中出现的《运营类项目风险地图》《中建八局二公司运营类风险要素清单》摘要等 wiki 依据，就是闭环已生效的直接证据。易忽略点：批量导入历史文档时应考虑临时关闭 autoEmbedOnWrite，否则逐条建索引会显著拖慢导入速度。

2.3 依赖关系要点

什么是依赖关系：若模块 A 运行时需要调用模块 B，则称 A 依赖 B（图中箭头由 A 指向 B）。依赖关系决定了改动的影响范围——改动 B 可能影响所有依赖它的模块，改动 A 则只影响 A 自己。

本系统四条核心依赖：

依赖关系方向与含义为什么这样设计
合同审查 → 知识库contractDrivenReview 依赖 hybridQuery 检索 wiki 集合，反向补全「标准规则清单未覆盖」的隐患审查需要"制度依据"作参照；复用既有检索能力，不另建一套
信息收集 → 知识库采集摘要经 /api/wiki/save → store.writeDocument，因 autoEmbedOnWrite 默认开启而即时进索引、可检索让采集成果立刻变成可检索资产，而非沉睡的孤立文本
业务层 → 统一 LLM 出口intake.ts 与 review.ts 共用同一 LLM 后端（本地 llama.cpp 或远程 chatComplete），经 settings 统一配置避免"问答能跑、审查报错"的配置漂移；换模型只需改一处
所有持久化 → SQLite 统一接口所有落库均经 src/db.ts 的 Database 接口（本次为其补 transaction 声明）统一连接管理与迁移入口；屏蔽 better-sqlite3 / bun:sqlite 差异

依赖方向的关键结论：

  • 无循环依赖：业务层依赖能力层与存储层，但能力层 / 存储层从不反向依赖业务层。因此新增业务模块（如合同审查）不会影响既有能力。
  • 能力层被多点复用：hybridQuery 与 LLM 出口同时服务于问答（/api/query）、信息收集与合同审查——这是"改动要格外小心"的地方，故新增参数必须可选且带默认值。
  • 脚本与前端是并列入口：二者都只依赖应用层或直接依赖业务层，互不依赖，因此去掉前端不影响脚本运行（这对无人值守的批处理很重要）。

2.4 重点、常见误区与易忽略细节

最该记住的三条结论（若只记三件事）：

  1. 依赖严格单向、自上而下（接入层 → 应用层 → 业务层 → 能力层 / 存储层）。任何"反向调用"都是设计异味，也是判断改动是否安全的第一准则。
  2. 检索与 LLM 属于共享能力层，不是某个业务模块的私有物。新增业务必须复用，而非自建一套。
  3. 知识回流闭环是系统"越用越聪明"的根因：写入即索引 → 下次可检索 → 成为新报告的制度依据。

常见误区（按被发现频率排序）：

误区正解
以为 /api/review 会跑反向审查实际只跑正向（reviewContract）；反向因耗时长由 scripts/ 直接调用，绕过 HTTP 以免请求超时

容易被忽略的细节：

  • autoEmbedOnWrite 默认开启——既是"写入即可检索"的便利来源，也是批量导入变慢的潜在原因（大批量导入时可考虑临时关闭）。
  • intake.ts 内置无 LLM 兜底路径，因此未配置模型时信息收集仍可运行，只是问题质量下降——排查"问答变笨"时要想到这一点。
  • db.ts 的 Database 是自定义最小接口，本次补 transaction 仅改 TS 类型、不改运行时行为（底层驱动本就提供该方法）。
  • MAX_FRAGMENTS 不只是"调参"，而是防超时的必要手段：本次 23 个片段已产出 233 个风险点，全量约 40 片段耗时更长，建议先小批量验证再全量跑。
  • wiki 导航 index.md 由 src/wiki/index-gen.ts 生成，若手工新增 wiki 文件而未重建索引，该页不会出现在导航中（需执行 qmd wiki index <wiki集合>）。
  • 反向审查的每条结论都同时带「合同映射」与「wiki 制度依据」两个来源，缺一不可溯源——这是双域检索（合同域 / wiki 域）存在的意义。

3.1 总体定位与兼容总原则

背景与动机：原始项目是一个通用的文档知识引擎（任意 PDF/DOCX/Markdown 都能检索与阅读）。但在实际业务（如工程/教育/能源行业的合同管理）中，用户需要的不是"泛泛地搜文档"，而是"拿着一份标准风险清单，逐条核对这份合同有没有坑"。这种需求在原项目里没有现成支撑——它需要把"检索能力"与"领域规则 + LLM 判定"组合起来。本改动的目的就是在不破坏原通用能力的前提下，叠加这样一层垂直应用。

应用场景示例：某幼儿园运营方拿到了一份《联营合作协议》，希望对照《中建八局二公司运营类风险要素清单》（44 项）快速知道"哪些条款踩了红线、哪些条款清单里根本没提但仍有隐患"。按原项目只能人工通读；叠加本层后，一条命令即可产出结构化评审报告。

维度说明
调整定位在原生三大能力之上叠加一个「合同风险审查」垂直应用层，而非替换或重构核心检索 / 阅读 / 摄取逻辑。
兼容总原则① 复用现有 hybridQuery / Store / Database / settings(LLM) / 索引与 wiki，不另起一套检索；② 新增代码集中落在 src/contract-review/，对核心文件只做最小增量；③ 数据模型通过追加式迁移扩展，不 ALTER 原表；④ 所有新增参数均为可选且带默认，旧调用方零感知。
修改目标让原项目从一个「通用文档知识引擎」升级为「可对任意合同集合做结构化风险审查 + 预料外隐患发现」的领域化工具，同时保持其 agent-native / 100% 本地优先的原有定位。
预期效果一份合同包即可产出：① 对照标准风险清单的逐项评审报告；② 从合同出发反查知识库、捕捉清单未覆盖的预料外风险报告；③ 可持久化、可列管、可复现的审查记录。
约束条件不得破坏原 Retrieve/DeepRead/Ingest 行为；不得引入核心层新依赖；迁移必须幂等；LLM 调用必须走与原 rag.ts 同源的统一出口。

分步骤落地策略（本次即按此顺序实施）：

  1. 识别复用点：确认检索（hybridQuery）、存储（Store/Database）、配置（settings）、知识库（wiki 集合）均可直接复用，无需重写。
  2. 隔离新增代码：所有审查专属逻辑放入独立目录 src/contract-review/，核心文件仅做最小增量。
  3. 追加数据模型：在迁移链里新增三张表，保证老库升级不丢数据。
  4. 暴露入口：先补 API 路由与 CLI 子命令，再补前端面板，层层递进。
  5. 闭环验证：用 scripts/ 脚本跑通正向 + 反向两条管线，并以增量落盘保证长任务可中断续跑。

3.2 模块一 · 新增合同审查引擎 src/contract-review/

背景与动机：为什么需要两条管线？因为单一视角都有盲区——正向（规则驱动）保证"标准清单上的 44 条一条都不漏"，但清单本身可能过时或不完整；反向（合同驱动）则从合同文本出发，让 LLM 自由发现"清单没写、但明显有风险"的预料外问题。两者互补才能既"合规覆盘"又"查漏补缺"。

维度说明
调整模块/功能新增整目录模块：review.ts（引擎）、prompt.ts（提示词）、db.ts（持久化 CRUD）、risk-rules-seed.ts（风险规则种子）。原项目无此目录，属纯新增。
实现方向双向管线：
① 正向（规则驱动） reviewContract()：抽取项目信息 → 逐条规则 hybridQuery 反查「合同域 + wiki 域」→ LLM 严格 JSON 判定（触发/未触发/未找到 + 等级 + 建议）→ 三段式报告 → 持久化；
② 反向（合同驱动） contractDrivenReview()：splitClauses() 分句 → 每句反查 wiki → LLM 标记 expected/unexpected 风险 → 循环内增量写 partial 报告 → 合成预料外报告。辅以 retrieveForRule()、extractJsonObject/Array() 等工具函数。
兼容方式引擎只消费原项目公开能力（hybridQuery、Store.db、getSettings、getWikiCollections），不修改其核心实现；报告写入沿用原 content/documents 之外的独立表。
修改目标把「检索 + LLM 判定」封装成可复用的合同审查流水线，对原项目零侵入。
预期效果产出结构化风险报告（含 wiki 制度依据），并额外发现标准清单未覆盖的预料外隐患（本次试运行 23 片段中预料外占比约 56%）。
约束条件必须复用 hybridQuery 而非自建检索；LLM 调用须走统一 settings.llmBaseUrl/llmModel/llmApiKey；任一步 LLM 失败须降级而非崩溃（保留 error finding / 空风险并继续）；禁止写原 content、documents 表。

正向管线分步骤（reviewContract）：

  1. getCollectionBodies() 取合同集合全部激活文档正文（单文档则取该文档）。
  2. chatComplete(REVIEW_SYSTEM_PROMPT, buildProjectInfoPrompt(...)) 抽取 10 项项目信息（名称/主体/期限/模式/投资/收益/退出/违约/保险/争议解决）。
  3. 对每条启用规则：retrieveForRule() 分别检索"合同域"与"wiki 域"，拼入 buildRuleEvaluationPrompt 交 LLM 输出严格 JSON。
  4. composeReport() 生成"项目信息 / 逐条评审 / 总体评价"三段式 markdown，并 upsertContractMeta + insertAnalysisRecord 落库。

反向管线分步骤（contractDrivenReview）：

  1. splitClauses() 按"第X条/段落"把合同切成条款级片段，过滤短于 24 字的无意义段。
  2. 对每条款：hybridQuery 反查 wiki 背景，调用 buildContractDrivenPrompt 让 LLM 输出 [{type, matchedRule, description, severity, suggestion}, ...]。
  3. 每处理完一条即增量写 *-partial.md，长任务被超时打断也能保留已审结果。
  4. 循环结束合成"预料内 / 预料外"占比概览与逐片段发现报告。

背景与动机：审查结果若不落库，每次都要重跑 LLM（昂贵且慢），也无法"上次的报告去哪了"。因此需要三张与原索引/文档解耦的表来存放"规则库 / 合同档案 / 分析记录"，且必须做到升级旧库时不破坏原有 content/documents 表。

维度说明

  1. 在 db-schema.ts 迁移链末尾新增 CREATE TABLE IF NOT EXISTS 三条语句（IF NOT EXISTS 保证幂等）。

3.4 模块三 · 检索与索引能力增强 hybrid-search.ts / store.ts / backends/indexing.ts

背景与动机：原 hybridQuery 面向"在全库里搜一段文本"，但审查有两个特殊诉求：① 要能限定检索范围（只在合同里找依据、只在 wiki 里找制度），否则合同条文会和背景知识混在一起无法溯源；② 采集到的摘要希望写入即建索引，立刻可被后续审查检索到，形成"越用越聪明"的知识闭环。

维度说明

实现方向审查时以「合同集合」为审查对象、「wiki 集合」为背景参考，分两次 hybridQuery 调用保持来源清晰；采集摘要写入 wiki 即自动进索引，形成知识闭环。
兼容方式新增参数全部可选且带默认，原调用方（/api/query、/api/ask、Deep Read 等）行为与返回结构不变。
修改目标在不改核心检索语义的前提下，支撑「合同为对象、wiki 为背景」的双域检索与即时索引。
预期效果反向审查可精准反查知识库；采集摘要写入后即可被检索，由孤立文本变为可检索资产。
约束条件默认路径与返回契约必须向后兼容；skipRerank/minScore 仅作审查内加速用，不得影响默认重排质量。

4.2.1 项目定位与核心闭环

  • 定位：MinerU Document Explorer（命令入口统一为 qmd），把 Markdown / PDF / DOCX / PPTX 变成"可搜索、可精读、可持续写入的知识库"。

4.2.2 三种检索模式与混合检索管线

模式实现特点与适用
searchBM25 / FTS5 全文快、零模型、零门槛；适合专有名词、错误码、编号
vsearch向量语义同义 / 概念召回
queryFTS + 向量 + 查询扩展 + LLM 重排默认推荐，质量最好

混合检索 8 步管线（architecture.md，本次改动复用的正是这条管线）：

  1. 初始 FTS 扫描；强信号短路：top1 得分 ≥ 0.85 且领先第 2 名 ≥ 0.15 → 跳过查询扩展。
  2. 查询扩展（微调模型）生成 lex / vec / hyde 变体并去重。
  3. 并行检索：每个查询同时走 FTS 与向量，原始查询给予 ×2 权重。
  4. RRF 融合 score = Σ(weight/(k+rank+1))，k = 60；第 1 名 +0.05、第 2–3 名 +0.02。
  5. 取 Top 40 送入重排。
  6. LLM 交叉编码重排（qwen3-reranker，以 logprob 作为置信度）。
  7. 位置感知混合：blended = rrfWeight×(1/rrfRank) + (1-rrfWeight)×rerankScore，rank 1–3 → 0.75、4–10 → 0.60、11+ → 0.40。
  8. 分数归一化：FTS abs(s)/(1+abs(s))；向量 1-distance；重排直接取 logprob。

分数解读：0.8–1.0 高度相关｜0.5–0.8 中等｜0.2–0.5 部分相关｜0.0–0.2 低相关。与本次改动的关联：3.4 节为 hybridQuery 新增的 collections / skipRerank / minScore 正是对第 1、6 步的可选干预。

4.2.3 查询语法（SYNTAX.md）

  • lex：BM25 关键词，支持 word 前缀匹配、"phrase" 精确短语、-word / -"phrase" 排除。
  • vec：向量语义查询。
  • hyde：假设性答案嵌入——先写一段 50–100 词的"预期答案"，再以其向量检索。
  • intent：背景说明，用于消歧；本身不检索、不能单独出现，须至少配一条 lex:/vec:/hyde:。
  • 权重规则：多行查询中第一行权重为 2 倍；融合时原始查询也 ×2。

4.3.2 检索链路性能排障（五个瓶颈与修复）

为什么重排最贵：cross-encoder 必须把 query 与每个候选逐对拼接各跑一次完整前向，中间结果无法复用；每生成一个 token 都要把整套 640MB 权重读一遍。相比之下嵌入是 bi-encoder，文档向量已离线预计算进 SQLite，在线只需为很短的 query 算一次。

阶段症状 → 根因 → 修复 → 收益
T0重排 7 块耗时 261s ← 集显被当成加速器 → 初始化关闭卸载、强制纯 CPU → 回落至分钟级
T1冷查询 141s / 二次 11s ← 杀软实时扫描 GGUF → 仅对 models/ 加信任（勿扩大到整个缓存目录）→ 秒级
T2带 grammar 的查询扩展永久卡死 ← 上游采样器结束符死循环 → 升级 node-llama-cpp 3.17.1→3.20.0 + 弃用 grammar，改自由生成 + 容错行解析
T3每次调用重新加载模型 ~205s → 改为常驻服务（模型只载一次）→ 205.4s → 1.2s（164×）
T4完整检索 >4min 超时 → 把"跳过重排"开关接到 CLI 与工具层并默认关闭（需最高精度时用 --rerank）→ 270s+ → 8.9s

运维要点：常驻服务是前置依赖（qmd mcp --http --daemon）；服务仅监听 IPv6（127.0.0.1 连不上，须用 localhost / [::1]）；上下文空闲 5 分钟后释放、下次透明重建（权重不清空，故仍远快于冷启动）。这条经验直接解释了本报告 3.2 中"反向审查为何走脚本而非 HTTP"——长任务必须用常驻或脚本方式，避免重复加载与超时。

4.3.3 向量索引重建复盘（四个问题与根因）

问题现象 → 根因 → 结论
问题一Cannot read properties of undefined (reading 'prepare') ← 项目有两层 store：SDK 层 QMDStore（无 db 属性）与内部 InternalStore（有 db）；server.ts 导入前者却用 as any 直接调底层函数 → store.db 为 undefined。根因是 as any 让 TS 失去保护；修复为改调 store.embed({...})
问题二"一直显示重建中" ← 排除死循环/参数/下载/编译后，实测确认为 CPU 算力下限（4 核跑 300M 模型约 20ms/token）。关键误判：用数据库已有向量行数（32）反推 chunk 数得出 ETA 6–7 分钟，实际 73 个 chunk，ETA 被低估一倍以上——ETA 必须直接调用分词函数测量
问题三服务器崩溃 + 前端计时空转（出现 762s / 1324s 假象）← 进程崩溃后请求永不 resolve，setInterval 继续走。改进：启动带日志重定向，正是靠日志中的 POST /api/embed (2168856ms) 才确认那次其实已成功（约 36 分钟）
问题四GPU 认知偏差（最重要的纠正）：检测到 llama.gpu="vulkan"、VRAM 8GB 就建议开启是错的——实为 Intel UHD 集显。上游"集显更慢"的结论基于 rerank 基准；而干净 A/B 实测（同任务、无并发）显示 embedding 场景下集显快约 7 倍（257s vs CPU 预估 30 分钟）。原则：上游性能结论不能跨模型、跨机器套用，必须本机实测。

耗时对比（exam 73 chunks）：CPU ≈ 30 分钟（97% 在推理）｜集显 Vulkan ≈ 4.3 分钟（准备升到 ~112s 但推理快 12×）→ 总提速约 7 倍。

被主动撤回的负优化（很有教育意义）：多上下文并行（本机 CPU 分支本就返回 1）、推理线程开满 8（4 物理核+超线程，单条从 12s 恶化到 48s）——均已还原。

遗留缺陷：exam 处于"部分嵌入"——库里只有 32 条向量、实际 73 个 chunk，而 getHashesNeedingEmbedding() 只统计"完全没有向量的文档 hash"，只要某 hash 存在任意一条向量就不再计入，导致缺失的 41 个 chunk 静默影响检索质量。根治方向：改为按 chunk 数比对。

4.3.4 对外接口、鉴权与配置

  • /api/ask 对外提问接口：POST + Authorization: Bearer <token>，返回标准 JSON（非流式）；全程在服务端完成检索与生成，调用方只传问题、不持有 LLM key。错误码：400 请求体非法｜401 token 无效｜500 检索失败；生成阶段失败仍返回 200，但 error 非空（多为 LLM 地址不可达）。
  • 鉴权红线：严禁用 QMD_ALLOW_ANONYMOUS=true 对外暴露——它会让所有 /api 路由匿名开放（含配置写入与用户管理）。正确做法是新增只读"查询 Token"作用域 + IP 白名单。
  • 账号登录：密码存为 scrypt$<saltHex>$<hashHex>（每账号随机 16 字节 salt）、timingSafeEqual 常量时间比较、5 次/分钟/IP 滑动窗口限流、失败统一返回 401「用户名或密码错误」以防范用户枚举；凭证校验抽象为可替换的 CredentialVerifier，预留对接 LDAP / OIDC。
  • 每用户专属配置：采用"全局默认层 + 每用户覆盖层"，通过 AsyncLocalStorage 传递用户上下文，使 getSettings() 自动返回合并结果而无需逐层透传 userId。核心安全设计是 USER_WRITABLE_SETTINGS 白名单——只放开检索数值与自带 key 的 LLM 配置，分块 / 索引 / 模型本体字段刻意不可写，因为索引是单实例内所有用户共享的。

4.3.5 Wiki 建库流程

  • 关键结论：wiki 与 raw 共用同一套建库管线，唯一区别是 store_collections.type='wiki'，从而在查询期被自动并入混合检索；无需为已有 raw 集合重建索引。
  • 11 步管线：collection add → 校验同名/同 path+pattern → 写 ~/.config/qmd/index.yml → syncConfigToDb 写入 SQLite → indexFiles() → glob 发现 → 后端解析 → chunking.ts 分块 → llm.ts embed() → 写 documents/content/vec0/FTS5/links → 提交事务。
  • 查询期：resolveHybridCollections() 扫描 type='wiki' 集合并入检索列表，命中结果标 kind:'wiki'；wiki 与 raw 共用同一 embedding 模型，语义空间一致，混合重排无偏差。

5.3 方法论沉淀（可复用的经验）

  1. 叠加优于重构：为通用引擎增加垂直能力时，优先"新增隔离模块 + 复用既有能力"，而非改造核心。既降低风险，也让改动易于向上游合并。
  2. 双向视角互补：单靠"标准清单"会漏（清单本身不完整），单靠"模型自由发挥"会飘（缺乏判定基准）。规则驱动 + 数据驱动双管线并用，才能既覆盘又查漏——56% 的预料外占比就是最直接的证据。
  3. 检索要混合、要分域：向量负责语义、BM25 负责精确条款号；审查时按"合同域 / wiki 域"分开检索，结论才可溯源。
  4. 长任务必须增量落盘：与 LLM 打交道的流水线动辄数十分钟，把"写结果"放进循环而非放在最后，是低成本高收益的可靠性设计。
  5. 配置出口要唯一：所有模型调用走同一处配置，杜绝"问答能用、审查报错"的配置漂移。
  6. 诚实标注未完成项：如 CLI 子命令标注为"规划中"而非含糊带过，避免读者误判实现程度——这也是本报告刻意遵循的原则。
