一、概述与适用范围

本流程把“制度/模板知识”与“合同审查”打通：先由运营制度文件、风险清单、合同样例沉淀为结构化 知识库（wiki），再在合同审查时，对每一条风险规则同时检索合同条款与 wiki 制度依据，最终输出的报告里逐条标注本条风险所引用的 wiki 页面，做到“风险可追溯、建议有出处”。

核心价值：过去审查只给结论；现在每条发现都附带「制度/模板依据（来自运营知识库 wiki）：×××、×××」，审查意见可直接对应到《运营类风险要素清单》《运营项目风险地图》等制度原文，便于合规复核与谈判交底。

三、前置准备

3.1 运行环境

  • 运行时：bun（≥1.4）或 node ≥18。
  • 数据库：默认索引库 ~/.cache/qmd/index.sqlite（生产模式自动定位，测试需设 INDEX_PATH）。
  • 集合划分：yunying（原始源文件，type=raw）、yunyingwiki（知识库，type=wiki）。

3.2 LLM / 嵌入 / 重排模型

  • 对话模型：用于“项目信息抽取 + 逐条风险评审 + 总体评价”（chatComplete）。
  • 嵌入模型：向量化 wiki 与合同，供 hybridQuery 召回。
  • 重排模型（可选）：rerank 阶段对候选精排。
注意：必须先在 QMD 设置中配置可用的对话模型端点（baseUrl / model）。未配置时，检索与报告撰写逻辑仍可用，但 LLM 评审会失败，每条发现会回退为“error/建议补充”，wiki 依据仍会正常生成。

四、阶段一：构建运营知识库（wiki）

知识库由制度原文与合同样例经解析、写入、向量化、索引生成、质量检查五个步骤形成。当前 yunyingwiki 共 17 个页面，含概念页（如《运营类项目风险地图》《委托运营（能源托管）类合同审查要点》）、手册/办法摘要、风险清单摘要、合同样例等。

4.1 写入 wiki 页面（程序化 API，已验证）

import { createStore, getDefaultDbPath, enableProductionMode } from "./src/store.js";
import { generateWikiIndex } from "./src/wiki/index-gen.js";
import { lintWiki } from "./src/wiki/lint.js";

enableProductionMode();
const store = createStore(getDefaultDbPath());
const db = store.db;

// 1) 写一页：frontmatter(title/type/sources) + 正文（支持 [[wikilink]]）
const fm = `---\ntitle: 委托运营（能源托管）类合同审查要点\ntype: concept\nsources:\n  - yunying/济南高新区空港新城幼儿园-临港小镇幼儿园.docx\n---\n\n# 委托运营（能源托管）类合同审查要点\n...正文，可引用 [[concepts/运营风险地图]] ...`;
await store.writeDocument("yunyingwiki", "concepts/审查要点.md", fm, "委托运营（能源托管）类合同审查要点");

// 2) 重新生成索引页
const idx = generateWikiIndex(db, { collection: "yunyingwiki" });
await store.writeDocument("yunyingwiki", "index.md", idx.markdown, "运营 Wiki 索引");

// 3) 向量化（force 全量重算）
await store.embed({ collections: ["yunyingwiki"], force: true });

// 4) 质量检查：孤儿页 / 断链 / 源过期
const r = lintWiki(db, { collection: "yunyingwiki", stale_days: 30 });
console.log(r.orphan_pages, r.broken_links, r.suggestions);

4.2 也可用 CLI / MCP

  • CLI：qmd collection add <文件夹> <名称> --wiki 注册 wiki 集合，再 qmd index 与 qmd embed。
  • MCP 工具：wiki_write_document / wiki_lint 等。

4.3 质量门禁（wiki_lint）

检查项含义处理
orphan_pages无任何入链/出链的孤立页补充 wikilink 或从 index 链接
broken_links指向不存在页面的链接修正路径或新建目标页
stale_sources源文件改动后未同步的页面重新生成该页

实测：17 页 wiki，orphan=[]、broken=[]、suggestions=[]，质量门禁通过。

六、阶段三：合同审查端到端

入口函数 reviewContract(store, opts)，opts 含 collection（或 path 指定单份合同）、tags、reportDir。

6.1 建立专用审查集合（避免检索串味）

// 把待审合同挂到独立集合（复用已有 content hash，不重复入库）
INSERT OR IGNORE INTO store_collections (name, path, pattern, type, include_by_default)
  VALUES ('kindergarten-heating', './kindergarten-heating', '**/*', 'contract', 1);
INSERT OR IGNORE INTO documents (collection, path, title, hash, created_at, modified_at, active)
  VALUES ('kindergarten-heating', '<合同文件名>', '<标题>', '<合同hash>', datetime('now'), datetime('now'), 1);

6.2 reviewContract 执行流程

  1. 项目信息抽取：LLM 从合同正文抽取项目名称、主体、期限、模式、投资/收益、退出、违约、争议等条目。
  2. 逐条检索 + 评审（核心）：对 44 条规则各执行一次 retrieveForRule：
    • 用 rule.name + rule.description 在合同集合检索相关条款片段；
    • 同时在 yunyingwiki 检索制度依据，返回命中的 wiki 页面标题列表 wikiRefs；
    • 把“合同片段 + wiki 依据 + 命中的 wiki 页面清单”拼成 prompt，交由 LLM 判定 triggered/not_found、摘录、解析、等级、建议。
  3. 总体评价：LLM 汇总 TOP5 风险、底线条款、谈判优先级、内部审批提示。
  4. 报告撰写 + 落库：composeReport 生成 Markdown，写入 reports/ 并登记 analysis_records。
wiki 依据如何进入报告（代码链路）： retrieveForRule() 返回 { retrieved, kbRetrieved, wikiRefs } → 写入 RuleFinding.wikiRefs → composeReport() 在每条发现末追加一行 - 制度/模板依据（来自运营知识库 wiki）：<wikiRefs 标题以“、”连接>。

6.3 一键运行脚本

bun scripts/run-review-kindergarten.ts

七、阶段四：报告解读与 wiki 依据呈现

报告分三大部分：①项目基本信息；②对照风险清单逐项评审（每条含“合同映射/原文摘录/解析/等级/建议/制度依据”）；③总体评价与谈判优先级。

7.2 wiki 依据在报告中的实际呈现（节选自 OPS-016 价格与成本锁定风险）

16. 第16项｜价格与成本锁定风险（OPS-016）
   - 合同映射情况：已触发
   - 风险条款原文摘录：3.1 本项目运营期限为15年……4.1 供暖单价为 26.7 元/㎡……
   - 风险解析：合同第3.1款约定运营期限为15年，第4.1款约定供暖单价固定为26.7元/㎡……
                        长期固定单价且缺乏调价机制，使成本上涨风险主要由乙方承担，触发价格与成本锁定风险。
   - 风险等级：高
   - 修改建议：建议将第4.1款“供暖单价为26.7元/㎡”修改为“基准供暖单价为26.7元/㎡，并按下列调价机制调整”：
                        ① CPI/能源价格累计变化超±5%时单价按公式自动调整；② 电价/税收优惠取消同步触发调价；
                        ③ 协商不成由当地发改委核定；④ 政策变更致项目无意义时乙方有权退出并收回投资。
   - 制度/模板依据（来自运营知识库 wiki）：济南高新区空港新城幼儿园供热运维服务合同（样例）、
                        运营类项目风险地图、《中建八局二公司运营类风险要素清单》摘要（司函字〔2026〕63号）、
                        委托运营（能源托管）类合同审查要点
可以看到：即使 LLM 判为“已触发/高”，其修改建议也与 wiki 中《风险地图》《委托运营审查要点》的“价格与成本锁定 / 调价机制”要求一一对应，审查意见因此可追溯到具体制度页面。

九、常见问题排查

现象原因 / 处理
报告里某条没有 wiki 依据该条 wikiRefs 为空，通常是 wiki 未向量化或检索阈值过高；执行 store.embed 后重跑。
所有发现都是“建议补充/error”对话模型未配置或不可达；wiki 依据仍会输出，仅 LLM 评审失败。
检索串味（混入无关源文件）审查集合未隔离；按 6.1 建专用集合只挂待审合同。
wiki_lint 报孤儿页新页未从 index 或被其它页链接；补充 wikilink 或重建索引。
Database path not set非生产模式需用 createStore(显式路径) 或先 enableProductionMode()。
